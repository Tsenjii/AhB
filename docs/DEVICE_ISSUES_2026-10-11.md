# AhB Android 實機問題追蹤（2026-10-11）

使用者實測回報（不是 CI 模擬）：同時開啟所有目前使用的 Gateway 只約 100 MB RAM；DeepSeek Web 無法成功使用、模型清單含大量不能推論的項目；Playground 無真正可點選模型；FreeBuff 登入失敗，另有 HTTP 502。

## 本輪程式修正

- **Playground 模型選擇：** 從 datalist 改成原生 `select` 下拉選單，保留手動輸入。新增「啟動並載入此來源模型」，由使用者主動觸發單一 Gateway 唤醒與即時目錄載入，不會自動輪流喚醒九個來源。
- **目錄不等於推論：** `/v1/models` 新增 `x_catalog_only:true`，休眠快取保留此標示；總覽對目錄模型顯示未經實測。DeepSeek Web 實驗版的靜態目錄不列入 Playground 選擇清單，但不會封鎖使用者手動輸入模型實測。
- **DeepSeek 帳號誠實狀態：** 單純 `accounts.txt` 存在並有憑證，只代表候選帳號，不當作「已經實際推論可用」。缺少帳號仍報未就緒，不會因此移除合法手動測試能力。
- **FreeBuff 登入狀態：** 官方授權碼與輪詢流程維持原契約；錯誤訊息現在區分取得 URL／輪詢階段、官方 HTTP 502/503/504、HTTP 429、401/403，以及網路或回應格式錯誤。**不要向本機 UI 回傳官方錯誤 body**，可能含敏感資訊。
- **RAM：** Android 新裝預設允許最多九個按需 Gateway 同時常駐，UI 提供全來源 9／86400 秒預設；既有 `config.json` 的使用者設定**不會被覆寫**。Linux 512MB 預設仍為單個／120 秒，避免將單一 Android 實測外推到 VPS。

## 尚未修復／必須實機核對

- DeepSeek Web 的聊天實際成敗及錯誤來源；目前上游 `/v1/models` 是靜態宣告，不是實測。需要使用者**自行且合法授權**的帳號與實際 Chat Completions 測試，單靠健康檢查或本機程式碼無法解決官方網站的反應。
- FreeBuff OAuth 在使用者實際網路環境能否返回官方授權 URL／成功 Token。官方 HTTP 502 時，必須區分「取得 URL」「輪詢」與「實際聊天」。**沒有證據表明這次能修好上游 502**。
- FreeBuff Node `/v1/models` 源頭也是靜態目錄；沒有實測成功的模型不可標為可用，也不要消耗使用者額度自動掃所有模型。
- 升級後若有 502，進入 Playground 指定 Gateway，觀察 HTTP 訊息、`/api/providers` 的最近請求狀態及本機的 `logs/<provider-id>.log`；發送診斷時只保留錯誤狀態與非敏感摘錄，**不要張貼 Token、Cookie、一次性授權網址、帳密或完整請求 Header**。
- 如需重試 FreeBuff 登入，應使用原生受控流程；若本機帳號已儲存且 Gateway 已啟動，使用「重新載入 FreeBuff 帳號」，再用 Playground 對**已授權**模型做真實測試。
- 最新 Android + Linux 原生編譯成功，只能表示功能可安裝；手機上帳號登入／DeepSeek／FreeBuff／網路環境問題仍是 UNVERIFIED，不能在報告寫已修復。

## 實機快速驗收

1. 從官方 prebuilt 安全更新，保留備份；確認新控制台「資源」有「全來源」預設（不應自動改寫原有設定）。
2. 進入 `/playground`，選擇 OpenCode，按「啟動並載入此來源模型」，下拉選單應能實際切換數個模型，且仍能手動輸入。
3. DeepSeek 的靜態模型選單應提示尚未驗證，不把無法保證成功的名稱作為推薦；只有手動輸入與明確實測的回應才有診斷價值。
4. FreeBuff「以 Google 登入」若失敗，畫面應能指出「取得授權網址／查詢授權狀態」及 HTTP 代碼，而不洩漏官方回傳內容。
5. 在實際短時間、多來源與長時間串流負載下用 `/api/runtime` 量測峰值 RSS；100MB 空閒數據不能作為負載保證。
