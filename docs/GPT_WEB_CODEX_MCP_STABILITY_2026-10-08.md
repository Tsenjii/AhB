# AhB: GPT Web, Codex OAuth, MCP and native tool-calling stability
Research and implementation update: 2026-10-08. Read with [TO_API_REGISTRY.json](TO_API_REGISTRY.json) and [device acceptance](DEVICE_ACCEPTANCE_2026-10-08.md).

## Non-negotiable baseline

The user's OpenCode provider **has passed real Android chat, SSE (147 data chunks then [DONE]) and initial structured `get_time` tool-call emission**. No provider yet has a documented complete **two-turn tool cycle** on the phone. Do not describe a provider as "OpenCode-equivalent" until it meets **both** tool emission and tool-result continuation, plus sustained error/rate-limit behavior.

**New test:** `scripts/test-tool-roundtrip.sh` runs a provider/model first with an OpenAI function definition, requires a native `tool_calls` JSON array with a valid function ID/name/arguments, submits a synthetic deterministic tool result as a second OpenAI chat turn, and requires a final assistant answer. It does *not* run shell commands generated by the model. The test is opt-in because it makes actual quota-consuming inference. Mock fixture `scripts/test-tool-roundtrip-fixture.sh` is enforced by CI. This tests normal Chat Completions tool protocol only; independent tests are still needed for Responses/Anthropic and concurrency/streaming.

## Three distinct meanings of "GPT Web/MCP/To-API"

1. **ChatGPT Web UI automation:** drives a browser and reads the ChatGPT conversation. This is not a stable standard model API; UI changes, session loss, browser overhead and request queues make it a poor choice for low-resource phone production.
2. **Codex OAuth -> compatible model API:** uses an eligible ChatGPT account's Codex service through a user-initiated sign-in. Can offer Chat Completions, Responses and structure-preserving tool calls as a local adapter, but most community proxies rely on undocumented backend interfaces. Subscription/Codex usage limits still apply; this is *not* an OpenAI API billing key and not a guarantee of unrestricted GPT models.
3. **MCP server:** a model tool server. Some GPT/Codex proxies expose `ask_codex` as an MCP tool, which lets an *existing agent* ask GPT, but MCP tool invocation is not the same as full native model function-call/tool-result continuation and is not an interchangeable `/v1/chat/completions` API.

Official current context: https://help.openai.com/en/articles/11369540-using-codex-with-your-chatgpt-plan and https://developers.openai.com/api/docs/guides/tools-connectors-mcp.

## What is actually implemented in AhB now

- Added a **`codex` preset** in `scripts/connect-bridge.sh` and phone UI with example local port `9879`, mapping to the Codex OAuth Proxy reference. This is **connector-only** and requires the user to already run an eligible, authorized, OpenAI-compatible local service. It does not download, install, launch or log into the third-party proxy.
- Existing `copilot/` native Go sidecar and `kimiweb/` experimental Python opt-in installer are unrelated. Do not label Copilot as a GPT ChatGPT account.
- Added `scripts/test-tool-roundtrip.sh` and CI fixture. This is the acceptance test for every existing and new provider before promoting its status to verified tool-capable. It must not be run against unauthorized/exhausted quota accounts.

## Kimi Web stability decision (important user report)

User recalls Kimi Web reverse proxies being unstable. Upstream Kimi Web adapter https://github.com/chopper1026/kimi2api documents multi-account pool, refresh and backoff but explicitly says it is not optimized for programmatic Tool Calling. That is *not a verified native tool loop*. Therefore:
- Keep `kimiweb/` **experimental, optional and OFF by default**. Do not list it as production-ready or as a replacement for a known-good OpenCode tool-capable route.
- Do not add failover from a successful native tool-call source to a Kimi Web route unless that Kimi route has proven protocol-equivalent behavior and identical model/tool schema support.
- Validate web-session expiry, access errors, 429/503, account-recovery logic, SSE cancellation and full tool cycle before reconsidering.
- Separate `kimiweb/` from **Kimi Code**: their login/entitlement/runtime differs.

## Proposed reliability scoreboard (future implementation; not all implemented)

| Test | What passing means |
|---|---|
| Health | Local service starts reliably and never advertises a dead endpoint as healthy |
| Credential validity | Own account is authenticated, but does not claim unverified quota |
| Quota | Actual model can accept requests; 401/429/503 not hidden as process health |
| Models | Namespaced genuine upstream IDs, no fake advertised ability |
| Chat | Multiple ordinary requests return correct schema |
| True SSE | Real incremental chunks, client cancellation survives |
| Native tool call | Structured `tool_calls` with valid JSON arguments and stable call IDs |
| Full tool cycle | `tool_calls` -> `role=tool` response -> final model answer |
| Responses/Anthropic | Independently native/faithfully translated, not guessed |
| Restart | Credentials/config persist after stop/start and preserved upgrade |
| Extended stability | Repeated sequential/concurrent prompts within legitimate quota; backoff/rate-limit correctness |

Next work: first get a Codex candidate independently compiled for Android ARM64 *with licensing and actual login support confirmed*, then a manual real-device login/tool-cycle test. Add one mature Codex implementation as an optional sidecar only after meeting that bar; do not bundle two competing Codex proxies merely because they exist.

No CAPTCHA/anti-bot bypass, challenge solving or account multiplication is part of this integration plan.
